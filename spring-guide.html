한 장 요약FastAPI와 비교폴더 지도자바 기초층별 해부프론트와 소통금요일: memo서버가 켜질 때코드에서 보인 것

한 장 요약: /student/list에 접속하면 생기는 일

지금까지 배운 건 결국 이 흐름 하나예요. 각 단계의 색은 아래 모든 섹션에서 같은 층을 뜻해요.

  1. 1
    브라우저 주소창에 localhost:8080/student/list 입력
    브라우저가 서버에 "GET /student/list 주세요"라는 요청을 보내요.
  2. 2
    Controller 주소에 맞는 메서드를 찾아 실행
    스프링 안에 들어 있는 서버(Tomcat)가 8080 포트에서 요청을 받아요. @RequestMapping("/student") + @GetMapping("/list")가 붙은 StudentController.getStudents()가 실행돼요.
  3. 3
    Service 컨트롤러가 일을 맡김
    컨트롤러는 직접 일하지 않고 studentService.getList()를 불러요.
  4. 4
    Repository DB에 SQL을 보냄
    서비스가 studentRepository.findAll()을 부르면, JPA가 select … from studenttbl SQL을 대신 만들어 Oracle에 보내요.
  5. 5
    DB → Entity 결과 행이 자바 객체로 바뀜
    테이블의 한 줄(row)이 Student 객체 하나가 돼요. 여러 줄이니 List<Student>로 돌아와요.
  6. 6
    DTO 서비스가 Entity를 DTO로 옮겨 담음
    Student의 값을 하나씩 꺼내 StudentDto에 넣어요. 화면에 나갈 상자는 DB용 객체와 따로 두는 거예요.
  7. 7
    Controller 데이터를 Model에 담아 화면 파일로 넘김
    model.addAttribute("list", list). 메서드가 void라서 주소와 같은 경로의 templates/student/list.html을 화면으로 써요.
  8. 8
    Thymeleaf → 브라우저 HTML 완성 후 응답
    th:each가 학생 수만큼 <tr>을 만들어 완성된 HTML을 브라우저로 보내요. 브라우저는 그걸 그대로 보여 줘요.
한 문장으로: Controller는 받고, Service는 일하고, Repository는 DB와 말하고, Entity는 테이블 모양이고, DTO는 밖으로 나가는 상자예요.

폴더를 이렇게 나누는 이유: 스프링은 DemoApplication.java가 있는 패키지(com.example.demo)와 그 아래 폴더만 훑어서 @Controller, @Service 같은 표시가 붙은 클래스를 찾아요. 그래서 컨트롤러를 com.example.demo 밖에 두면 스프링이 못 찾고 404가 나요.

basic 폴더는 스프링이 아닌 순수 자바 연습용이에요. src/에 코드, lib/에 직접 넣은 lombok.jar, bin/에 컴파일된 .class 파일이 있어요.

자바 기초 (basic 폴더)

클래스와 객체

클래스는 붕어빵 틀, 객체는 틀로 찍어 낸 붕어빵이에요. 틀만 있으면 아무것도 못 하고, new로 찍어 내야 쓸 수 있어요.

// basic/src/ch1/BoardMain.java
User user = new User(1L, "홍길동", "hong123@gmail.com");
Board board = new Board(1L, "게시글", "게시글", user);

파이썬이라면 user = User(1, "홍길동", ...)라고 쓸 거예요. 자바는 앞에 타입(User)을 적고, 앞에 new를 붙여요.

타입을 먼저 적는다

String name = "홍길동";       // 문자열
Long id = 1L;                 // 큰 정수. 숫자 뒤 L = Long이라는 표시
List<StudentDto> list;        // StudentDto만 담을 수 있는 리스트

파이썬 리스트는 아무 타입이나 섞어 담을 수 있지만, 자바는 <> 안에 무엇을 담을지 정해요.

종류기본 타입 (소문자)객체 타입 (대문자)
정수int, longInteger, Long
실수float, doubleFloat, Double
문자 / 문자열char ('a')Character, String ("a")

Entity의 id가 long이 아니라 Long인 이유: 객체 타입은 null(값 없음)을 가질 수 있어요. 아직 DB에 저장하기 전에는 id가 없으니 null이어야 해요.

필드, 생성자, 오버로딩

// basic/src/ch1/Board.java
public class Board {
    private Long id;          // 필드: 객체가 가진 값
    private String title;
    private User user;        // 다른 객체도 필드가 될 수 있음

    // 생성자: new 할 때 실행, 필드 초기화 담당
    public Board(Long id, String title, String contents) { … }

    // 같은 이름 생성자를 파라미터 개수만 다르게 하나 더 → 오버로딩
    public Board(Long id, String title, String contents, User user) { … }
}
  • private: 이 클래스 안에서만 접근 가능. 밖에서는 board.title로 직접 못 건드려요.
  • getter / setter: 그래서 getTitle(), setTitle() 메서드로 꺼내고 바꿔요.
  • toString(): 객체를 출력할 때 쓰는 글자. 직접 만들지 않으면 ch1.Board@6d06d69c처럼 알아보기 힘든 값이 나와요.

Lombok: 반복 코드를 대신 써 주는 도구

Board.java는 getter, setter, toString을 직접 써서 56줄이에요. User.java는 Lombok 어노테이션으로 같은 일을 해서 18줄이에요.

// basic/src/ch1/User.java
@ToString @Setter @Getter @AllArgsConstructor @NoArgsConstructor
public class User {
    private Long id;
    private String name;
    private String email;
}
어노테이션대신 만들어 주는 것
@Getter / @Setter모든 필드의 getXxx() / setXxx()
@NoArgsConstructor파라미터 없는 생성자 new User()
@AllArgsConstructor모든 필드를 받는 생성자 new User(1L, "홍길동", "…")
@RequiredArgsConstructorfinal 필드만 받는 생성자 (스프링 의존성 주입에 씀)
@ToString필드 값이 보이는 toString()
@BuilderUser.builder().name("홍길동").build() 식으로 만들기
@Log4j2log.info(...)로 로그 찍기
어노테이션(@)이란? 파이썬 데코레이터처럼 생겼지만, 스스로 무언가를 실행하지는 않아요. 클래스에 붙이는 표시표예요. Lombok이나 스프링이 그 표시를 보고 대신 코드를 만들거나 객체를 관리해 줘요.

층별 해부 (demo 폴더)

DB에서 가까운 층부터 올라가요. 만드는 순서도 보통 이 순서예요.

Entity

테이블 모양을 자바 클래스로

// demo/.../entity/Student.java (요약)
@EntityListeners(value = AuditingEntityListener.class)
@Table(name = "studenttbl")   // 테이블 이름
@Entity                        // 이 클래스 = DB 테이블
public class Student {
    @Id                                                 // PK
    @GeneratedValue(strategy = GenerationType.IDENTITY) // 번호 자동 증가
    private Long id;

    @Column(name = "sname", length = 50, nullable = false)
    private String name;

    @Enumerated(EnumType.STRING)   // enum을 글자로 저장 ("FRESHMAN")
    private Grade grade;

    @CreatedDate      private LocalDateTime createdDate;  // 저장 시각 자동 입력
    @LastModifiedDate private LocalDateTime updatedDate;  // 수정 시각 자동 입력
}

이 클래스를 만들고 서버를 켜면, application.properties의 ddl-auto=update 설정 때문에 studenttbl 테이블이 자동으로 생겨요. SQL로 CREATE TABLE을 직접 쓰지 않아도 돼요. 이렇게 객체와 테이블을 이어 주는 방식을 ORM이라고 하고, 자바의 ORM 표준이 JPA예요.

@CreatedDate가 동작하려면 DemoApplication.java에 @EnableJpaAuditing이 붙어 있어야 해요.

Repository

내용이 비어 있는데 동작하는 DB 창구

// demo/.../repository/StudentRepository.java
public interface StudentRepository extends JpaRepository<Student, Long> {
}

안이 비어 있는데도 동작해요. JpaRepository<Entity 이름, id 타입>을 이어받기만 하면, 스프링이 실행할 때 아래 메서드들을 자동으로 만들어 줘요.

메서드하는 일실행되는 SQL
save(student)저장 (id 없으면 새로, 있으면 수정)insert / update
findAll()전체 조회select * from …
findById(1L)하나 조회 (결과는 Optional)select … where id = 1
deleteById(1L)삭제delete … where id = 1
오늘 본 에러와 연결: findById()는 결과가 없을 수도 있어서 값을 Optional이라는 상자에 담아 줘요. 빈 상자에 .get()을 부르면 NoSuchElementException이 나요. 빈 테이블에서 readTest가 실패한 이유가 이거예요.
Service

실제 일 처리 + 의존성 주입

// demo/.../service/StudentService.java (요약)
@RequiredArgsConstructor
@Service
public class StudentService {
    private final StudentRepository studentRepository;  // new 하지 않았는데 쓸 수 있음

    public List<StudentDto> getList() {
        List<Student> list = studentRepository.findAll();
        List<StudentDto> students = new ArrayList<>();
        for (Student s : list) {               // Entity → DTO 옮겨 담기
            StudentDto dto = new StudentDto();
            dto.setId(s.getId());
            dto.setName(s.getName());
            …
            students.add(dto);
        }
        return students;
    }
}

왜 new 없이 쓸 수 있나요? (의존성 주입)

자바는 객체를 만들어야 그 기능을 쓸 수 있다고 했어요. 원래라면 서비스가 레포지토리를 직접 만들어야 해요.

스프링 없이

public class StudentService {
  StudentRepository repo;
  public StudentService() {
    repo = new StudentRepository();
  }
}

스프링에서

@RequiredArgsConstructor
@Service
public class StudentService {
  private final StudentRepository repo;
}
  1. 서버가 켜질 때 스프링이 @Service, @Controller, Repository 같은 표시가 붙은 클래스를 찾아서 미리 하나씩 만들어 보관해요. 이렇게 보관된 객체를 빈(Bean)이라고 하고, 보관하는 곳을 스프링 컨테이너라고 해요.
  2. @RequiredArgsConstructor가 final 필드를 받는 생성자를 만들어요.
  3. 스프링이 그 생성자에 보관해 둔 Repository를 넣어 줘요(주입).

FastAPI에서 db: Session = Depends(get_db)라고 쓰면 세션이 알아서 들어오던 것과 같은 원리예요.

Controller

주소와 메서드를 연결

// demo/.../controller/StudentController.java
@RequiredArgsConstructor
@RequestMapping("/student")   // 이 클래스의 공통 앞주소
@Controller
public class StudentController {
    private final StudentService studentService;

    @GetMapping("/list")      // GET /student/list
    public void getStudents(Model model) {
        List<StudentDto> list = studentService.getList();
        model.addAttribute("list", list);   // 화면에 "list"라는 이름으로 전달
    }
}
반환 타입어떤 화면 파일을 쓰나예
void요청 주소와 같은 경로/student/list → templates/student/list.html
String돌려준 글자와 같은 이름return "home"; → templates/home.html
DTO

왜 Entity를 그대로 보내지 않나요?

StudentDto는 Student와 필드가 거의 같은데 굳이 따로 만들어요. 이유는 세 가지예요.

  • 보안: 회원 Entity에는 비밀번호도 있어요. Entity를 그대로 내보내면 비밀번호까지 화면으로 나가요. DTO에는 보낼 것만 넣어요.
  • DB 보호: Entity는 DB와 연결된 객체라서, 값을 바꾸면 DB까지 바뀔 수 있어요. 화면 쪽에서 다루는 건 연결이 없는 DTO가 안전해요.
  • 모양이 달라도 됨: 로그인 화면은 아이디·비밀번호만 보내요. 그래서 LoginDto는 필드가 2개뿐이고, 대응하는 Entity도 없어요.

FastAPI에서 SQLAlchemy 모델과 Pydantic 스키마를 따로 만들던 것과 같은 이유예요.

프론트와 자바가 소통하는 원리

기본: 요청과 응답

프론트(브라우저, React)와 서버는 HTTP라는 약속으로 대화해요. 프론트가 요청을 보내면 서버가 응답 하나를 돌려줘요.

담기는 것예
요청메서드 + 주소 (+ 보낼 데이터)GET /student/list, POST /login + 아이디·비밀번호
응답상태 코드 + 내용200 + HTML, 200 + JSON

상태 코드: 200 성공, 404 그 주소에 연결된 기능 없음, 500 서버 코드에서 에러. 오늘 memo 서버에서 본 404는 MemoController가 비어 있어서 연결된 주소가 하나도 없었기 때문이에요.

응답의 내용을 무엇으로 보내느냐에 따라 방식이 둘로 나뉘어요.

방식 A. 서버가 HTML을 완성해서 보냄 (demo, @Controller)

<!-- demo/.../templates/student/list.html -->
<tr th:each="dto : ${list}">       <!-- list 안의 dto마다 한 줄씩 -->
  <td th:text="${dto.name}"></td>   <!-- dto.getName() 값으로 채움 -->
</tr>

${list}는 컨트롤러가 model.addAttribute("list", …)로 넣은 그 이름이에요. Thymeleaf가 서버에서 이 자리를 실제 값으로 바꾼 뒤, 완성된 HTML을 브라우저로 보내요. 브라우저는 받은 걸 보여 주기만 해요.

A-2. 화면 → 서버로 데이터 보내기: 로그인 폼

<!-- demo/.../templates/home.html -->
<form action="/login" method="post">
  <input type="text" name="id" />
  <input type="text" name="password" />
</form>

// demo/.../controller/HomeController.java
@PostMapping("/login")
public void postLogin(LoginDto dto) { log.info("로그인요청 {}", dto); }

// demo/.../dto/LoginDto.java
public class LoginDto { private String id; private String password; }

로그인 버튼을 누르면 브라우저가 id=hong&password=1234 같은 데이터를 POST /login으로 보내요. 스프링은 input의 name과 DTO의 필드 이름이 같은 것끼리 짝지어서 LoginDto를 자동으로 채워요. 이름이 하나라도 다르면 그 값은 null이 돼요.

방식 B. 데이터만 JSON으로 보내고, 화면은 React가 그림 (memo가 갈 방향)

ModelMapper: Entity ↔ DTO 자동 변환

demo: 한 필드씩 직접

StudentDto dto = new StudentDto();
dto.setId(s.getId());
dto.setName(s.getName());
dto.setGrade(s.getGrade());
dto.setCreatedDate(…);
dto.setUpdatedDate(…);

memo: 한 줄

MemoDto dto =
  modelMapper.map(memo, MemoDto.class);

필드 이름이 같은 것끼리 알아서 옮겨 줘요. build.gradle에 org.modelmapper:modelmapper를 추가하고, config/RootConfig.java에서 @Configuration + @Bean으로 스프링에 등록했어요. 등록해 두면 Service에서 private final ModelMapper modelMapper;로 주입받아 쓸 수 있어요.

@Bean은 @Service처럼 클래스에 붙이는 게 아니라, 직접 만든 객체를 빈으로 등록할 때 메서드에 붙여요. ModelMapper는 남이 만든 라이브러리라 클래스에 @Service를 붙일 수 없어서 이렇게 해요.

Setter 없는 Entity

// memo/.../entity/Memo.java: @Setter가 없음
public void changeText(String text) {
    this.text = text;
}

Student에는 @Setter가 있어서 아무 값이나 바꿀 수 있었어요. Memo는 @Setter를 빼고 바꿔도 되는 것만 메서드로 열어 뒀어요. 메모는 내용만 수정할 수 있고, id나 작성 시각은 못 바꾸게 막은 거예요.

Service의 CRUD 5개

메서드하는 일Repository 호출
create(dto)DTO → Entity로 바꿔 저장, 새 id 반환save()
read(id)하나 조회 후 DTO로findById()
readAll()전체 조회 후 DTO 리스트로findAll()
update(dto)찾아서 changeText()findById()
delete(id)삭제deleteById()

update()는 save()를 부르지 않아요. JPA는 조회해 온 Entity의 값이 바뀌면 그걸 기억해 뒀다가 자동으로 update SQL을 보내요. 이 기능을 변경 감지(dirty checking)라고 해요. 다만 이 자동 반영은 트랜잭션 안에서만 일어나고, 지금 MemoService에는 @Transactional이 없어요. 컨트롤러를 붙여서 실제로 수정해 볼 때 반영되는지 확인이 필요해요.

주의: 클래스 전체를 한 번에 실행하면 메서드 순서가 보장되지 않아요. 빈 테이블에서 readTest가 insertTest보다 먼저 돌면 실패해요. 오늘 본 에러가 이거예요. 실습할 때는 insert → read → update → delete 순서로 하나씩 실행하세요.

서버가 켜질 때 일어나는 일

터미널에서 ./gradlew bootRun을 치면 아래 순서로 진행돼요.

  1. 1
    Gradle이 라이브러리 준비
    build.gradle에 적힌 라이브러리를 받아요 (처음 한 번만 오래 걸림). npm install과 비슷해요.
  2. 2
    컴파일
    .java 파일을 컴퓨터가 실행할 수 있는 .class 파일로 바꿔 build/에 넣어요. 이때 Lombok이 getter·생성자 같은 코드를 채워 넣어요. 문법 오류가 있으면 여기서 멈춰요.
  3. 3
    main() 실행 → 스프링 시작
    SpringApplication.run(DemoApplication.class, args)가 스프링을 깨워요.
  4. 4
    빈 등록 (컴포넌트 스캔)
    com.example.demo 아래를 훑어서 Controller, Service, Repository를 만들어 보관하고, 서로 필요한 것끼리 주입해요.
  5. 5
    DB 연결 + 테이블 확인
    application.properties의 주소·계정으로 Oracle에 접속해요. ddl-auto=update라서 Entity와 테이블을 비교하고, 없거나 달라진 부분을 만들어요. Oracle이 꺼져 있으면 여기서 실패해요.
  6. 6
    Tomcat이 8080 포트를 열고 대기
    로그에 Tomcat started on port 8080, Started DemoApplication이 보이면 준비 완료예요. 이미 다른 서버가 8080을 쓰고 있으면 Port 8080 was already in use 에러가 나요.
서버가 안 켜질 때 확인 순서: Oracle 컨테이너가 켜져 있나 (OrbStack → oracle-db) → 8080을 다른 서버가 쓰고 있지 않나 → 로그의 첫 번째 Caused by 줄.
