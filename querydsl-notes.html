01 · 큰 그림

Querydsl은 왜 쓰나

「Spring 학습 노트」에서 이어지는 문서예요. 지금까지는 쿼리 메서드 이름(findByTitle)이나 @Query 문자열로 조회했어요. Querydsl은 같은 조회를 자바 코드로 조립하게 해 줘요.

조회 방법 세 가지 비교

방법생김새장점약점
쿼리 메서드findByTitleContaining(title)이름만 지으면 끝조건이 3개만 넘어도 이름이 끝없이 길어짐
@Query (JPQL)"SELECT count(b) from Board b"SQL처럼 자유롭게문자열이라 오타가 실행해야 드러남
Querydslboard.title.contains("title1")오타는 컴파일 에러, 자동완성, 조건을 변수에 담아 조립설정과 Q클래스 생성이 필요
FastAPI 쪽에서 보면

SQLAlchemy에서 select(Item).where(Item.name == "item1", Item.price > 20000)처럼 모델 속성으로 조건을 만들던 것과 같은 발상이에요. 자바는 ==, >를 이런 용도로 쓸 수 없어서 eq(), gt() 같은 메서드 이름으로 대신해요.

02 · 큰 그림

설정과 Q클래스

Querydsl은 Spring Boot starter가 없어서 build.gradle에 직접 세 줄을 넣어요.

querydsl-jpa

실제로 쿼리를 만들고 실행하는 라이브러리. 코드에서 import하는 것들(JPQLQuery, Tuple, JPAExpressions)이 여기 있어요.

querydsl-apt

컴파일할 때 @Entity를 찾아 Q클래스를 만들어 주는 도구. Lombok처럼 annotationProcessor로 등록해요.

:jakarta

Spring Boot 3부터 JPA 패키지가 javax.persistence → jakarta.persistence로 바뀌었어요. 이 꼬리표가 없으면 옛날 javax용이 받아져서 Q클래스가 안 생겨요.

jakarta.*-api 두 줄

apt가 @Entity, @Generated를 읽을 때 필요한 정의. 빠지면 빌드 중 "cannot find symbol"이 나요.

Q클래스는 어디에 생기나

book/build/generated/sources/annotationProcessor/java/main/com/example/book/entity/ ├── QBoard.java ← Board.java 에서 ├── QItem.java ← Item.java 에서 ├── QMember.java ├── QOrder.java ├── QOrderItem.java ├── QStudent.java └── … (@Entity 13개 → Q클래스 13개)

src가 아니라 build 아래에 생기는 자동 생성 파일이라 직접 고치지 않아요. Entity에 필드를 추가하면 다시 빌드해야 Q클래스에도 반영돼요. 테스트를 ▶로 돌리거나 ./gradlew compileJava를 하면 다시 만들어져요.

QItem 실제 생김새

① QItem.item

코드에서 QItem item = QItem.item;으로 꺼내 쓰는 그 객체예요. BoardTest 주석 "new 해서 새로운 객체 생성한 것과 같은 효과"가 이 뜻이에요. 이름 "item"은 JPQL의 별칭(from Item item)이 돼요.

② StringPath

필드 타입에 맞는 경로 객체가 생겨요. StringPath엔 contains, startsWith가 있고, NumberPath엔 gt, sum이 있어요. 그래서 숫자 필드에 contains를 쓰면 바로 빨간 줄이에요.

③ ListPath · QMember member

연관관계 필드도 경로가 돼요. QOrder 안에는 QMember member가 있어서 order.member.name처럼 점으로 따라갈 수 있어요.

필드명 기준이에요

Item의 name은 DB 컬럼이 item_name(@Column(name = "item_name"))이지만 Q클래스에선 item.name이에요. JPA처럼 Querydsl도 항상 자바 필드명으로 생각해요.

QuerydslPredicateExecutor

JpaRepository 옆에 interface 하나만 더 상속하면 "조건 객체를 받는 findAll"이 생겨요. 구현은 Spring Data가 해 줘요.

같은 방식으로 StudentRepository, ItemRepository, OrderRepository에도 붙였어요. 제네릭 자리에는 그 Repository의 Entity를 써요.

QueryDslTest 한 줄씩

조건을 만들 재료를 꺼내요. 변수 이름은 짧게 엔티티 이름 그대로 쓰는 게 관례.

student.name.eq("홍길동")

where sname = '홍길동'. 쿼리 메서드로 치면 findByName.

이 테스트는 결과를 출력하지 않아요

리턴값을 변수에 담거나 System.out.println하지 않아서 콘솔엔 SQL 로그만 찍혀요. 결과까지 보려면 BoardTest처럼 println으로 감싸요.

04 · 방법 1

조건식 → SQL 사전

아래 SQL은 10/27 테스트를 실제로 돌려서 얻은 Hibernate 로그예요. ? 자리에 들어간 값은 바로 아래 binding 로그에서 확인할 수 있어요.

자주 쓰는 조건

QuerydslSQL메모
name.eq("item1")= 'item1'같다 (equal)
name.ne("item1")<> 'item1'같지 않다 (not equal)
name.contains("t1")like '%t1%'포함
name.startsWith("item")like 'item%'~로 시작
name.endsWith("1")like '%1'~로 끝남
price.gt(20000)> 20000초과 (greater than)
price.goe(20000)>= 20000이상 (greater or equal)
price.lt(20000) · loe< · <=미만 · 이하
price.between(1, 5)between 1 and 5양 끝 포함
id.in(1L, 2L)in (1, 2)목록 중 하나
city.isNull()is nullisNotNull()도 있어요
a.and(b) · a.or(b)and · or조건 잇기. a.not()은 부정

실제 로그 ① eq + gt

결과가 [] 인 이유

item1의 가격은 i * 20000 = 정확히 20000이에요. gt는 초과라서 20000 > 20000은 거짓. 20000을 포함하려면 goe를 써야 해요.

실제 로그 ② contains · startsWith

like ?

값이 ?로 따로 전달돼요(바인드 파라미터). 사용자가 입력한 글자가 SQL에 그대로 섞이지 않아서 SQL 인젝션이 막혀요.

escape '!'

검색어 안에 진짜 %나 _ 글자가 있을 때 "와일드카드가 아니라 글자"라고 표시할 문자를 !로 정한 것. 신경 쓸 필요 없어요.

%title1%

contains는 앞뒤, startsWith는 뒤에만 %. 그래서 title1, title10 ~ title19, title100이 모두 걸렸어요 (12건).

연관관계 따라가기

Q클래스는 연관 필드도 경로로 갖고 있어서, "주문자 이름이 user1인 주문"을 객체를 만들지 않고 바로 표현할 수 있어요. order.member.name처럼 점으로 따라가면 Querydsl이 join을 대신 붙여 줘요. OrderTest 170~171줄의 주석 처리된 예제가 이 자리예요. 지금은 Member.builder().id(1L).build()로 가짜 Member를 만들어 비교하고 있는데, 경로를 따라가면 그럴 필요가 없어요.

05 · 방법 1

정렬과 페이징

게시판 목록처럼 "20개씩 끊어서 3페이지"를 만들 때 쓰는 부분이에요. BoardTest에서 101개 게시글로 연습했어요.

PageRequest.of(2, 20)의 2는 세 번째 페이지

페이지 번호는 0부터 세요. 0 = 1페이지, 1 = 2페이지, 2 = 3페이지. 그래서 앞의 40개를 건너뛰고 41번째부터 20개를 가져와요.

offset ? rows fetch first ? rows only

Oracle 12c 이후의 페이징 문법. MySQL이라면 limit 20 offset 40으로 나가요. DB가 바뀌어도 자바 코드는 그대로인 게 JPA의 장점.

count 쿼리

Page는 "전체 몇 페이지인지"도 알려 줘야 해서 개수 쿼리를 한 번 더 보내요. 101 ÷ 20 = 5.05 → 6페이지.

getSize()

한 페이지 크기(20). 실제로 담긴 개수가 아니라 요청한 크기예요.

getTotalElements()

조건에 맞는 전체 행 수(101).

getContent()

이번 페이지의 실제 데이터 List<Board>. 화면에 뿌릴 건 이거예요.

React와 연결하면

프론트에서 ?page=2&size=20을 보내고, 백엔드는 getContent()와 getTotalPages()를 함께 돌려주면 페이지 버튼을 그릴 수 있어요. 정렬도 PageRequest.of(2, 20, Sort.by("id").descending())처럼 Pageable 안에 함께 넣을 수 있어요.

06 · 방법 2

파일 3개의 연결

방법 1은 Entity 하나에 where를 거는 데까지예요. join이나 서브쿼리를 쓰려면 쿼리를 직접 조립하는 클래스를 만들고, 그걸 기존 Repository에 끼워 넣어요.

① 메뉴판QueryDslOrderRepository

직접 만들 메서드의 이름만 적은 interface. members(), items(), joinTest(), subQueryTest()

implements
② 주방QueryDslOrderRepositoryImpl

실제 쿼리를 짜는 클래스. QuerydslRepositorySupport를 상속해서 from()을 물려받아요.

extends (interface끼리 상속)
③ 창구OrderRepository

JpaRepository + ① 을 함께 상속. 바깥(테스트, Service)은 이것 하나만 주입받으면 save()도 joinTest()도 쓸 수 있어요.

Spring은 Impl을 어떻게 찾나

OrderRepository는 interface라 구현이 없는데도 orderRepository.members()가 동작해요. Spring Data가 시작할 때 "상속받은 interface 이름 + Impl"이라는 클래스를 찾아서 그 메서드를 연결하기 때문이에요.

interface찾는 클래스 이름
QueryDslOrderRepositoryQueryDslOrderRepositoryImpl ✓
QueryDslOrderRepositoryQueryDslOrderRepositoryImple ✗ (못 찾아서 서버 기동 실패)
이름이 계약이에요

Impl 클래스에 @Repository나 @Component를 안 붙였는데도 Bean이 되는 이유가 이 이름 규칙이에요. 철자가 하나라도 다르면 "No property 'members' found for type 'Order'" 같은 에러가 나요. 쿼리 메서드 이름으로 착각해서 파싱하려다 실패하는 거예요.

super(Order.class)

부모(QuerydslRepositorySupport)에게 "주로 Order를 다룬다"고 알려 줘요. 그렇다고 Order만 조회할 수 있는 건 아니라서 members()에서 Member도 조회해요.

QuerydslPredicateExecutor<Order>

OrderRepository에는 방법 1도 같이 붙어 있어요. 두 방법을 섞어 써도 돼요.

07 · 방법 2

from · where · select · fetch

SQL을 쓰는 순서와 거의 같아요. 다른 점은 from부터 시작하고, 마지막에 fetch()를 불러야 실제로 DB에 간다는 것.

from(member)

부모 클래스에서 물려받은 메서드. 쿼리 조립을 시작해요. 아직 DB엔 안 가요.

JPQLQuery<Member>

"조립 중인 쿼리" 객체. Querydsl은 결국 JPQL을 만들고, JPQL이 다시 SQL이 돼요.

.where(...).orderBy(member.name.desc())

조건과 정렬. 정렬도 Q클래스 경로로 써서 방법 1의 Sort.by("id")와 달리 오타가 컴파일 에러로 잡혀요.

query.select(member)

무엇을 꺼낼지. 엔티티 통째로면 생략해도 돼요(from(member)가 이미 Member 타입이라서).

query.fetch()

여기서 SQL이 실행되고 List가 돌아와요. 결과가 하나면 fetchOne(), 첫 번째만이면 fetchFirst().

메서드 체인으로 한 번에

수업 코드는 query.where(...), query.select(...)를 줄마다 나눠 썼는데, 각 메서드가 자기 자신을 돌려줘서 한 줄로 이어 써도 결과가 같아요. items()가 같은 모양이에요.

items()는 빈 리스트가 나와요

로그에 binding parameter (2:INTEGER) <- [200000]이 찍히고 결과는 []. 가장 비싼 item5도 100000원이라 20만 원 넘는 상품이 없어요. 주석은 "이상"인데 코드는 gt(초과)인 것도 같이 확인해 보세요. → 17번 탭

08 · 방법 2

join과 Tuple

주문과 주문자를 한 번에 꺼내는 쿼리예요. 두 종류의 엔티티를 함께 select하면 결과가 Tuple이라는 묶음으로 와요.

query.join(member)

inner join. 주문자가 없는 주문은 빠져요. 주문자 없는 것도 보려면 leftJoin.

.on(order.member.eq(member))

join 조건. "주문의 member가 이 member와 같다" = o.member_member_id = m.member_id. 엔티티끼리 비교하면 PK로 비교돼요.

select(order, member)

두 개를 꺼내니 JPQLQuery<Order>가 아니라 JPQLQuery<Tuple>이 돼요.

t.toArray()

Tuple을 Object[]로. [0]이 Order, [1]이 Member. 꺼낼 땐 형변환이 필요해요.

stream().map(...).collect(...)

React의 result.map(t => t.toArray())와 같아요. 자바는 List에 바로 map이 없어서 stream으로 바꿨다가 다시 List로 모아요.

Tuple에서 하나씩 꺼내기

Object[]로 바꾸지 않고 t.get(order), t.get(member)처럼 Q객체를 열쇠로 꺼내면 형변환 없이 타입이 맞게 나와요. 다만 Tuple은 Querydsl 타입이라 Repository 밖(Service, Controller)으로 내보내지 않는 게 보통이에요. 수업 코드가 Object[]로 바꿔서 돌려준 이유예요.

member_member_id 라는 컬럼 이름

Order의 member 필드에 @JoinColumn이 없어서 FK 이름이 "필드명_상대PK컬럼명" = member + _ + member_id로 정해졌어요. 이름을 정하고 싶으면 @JoinColumn(name = "member_id").

09 · 방법 2

서브쿼리

"주문 한 건마다 주문 상품이 몇 개고 합계가 얼마인지"를 같이 보여 주는 쿼리예요. select 안에 작은 select가 들어가요.

.join(member)...join(orderItem)

join을 이어 붙여 주문 · 주문자 · 주문상품 세 테이블을 연결.

JPAExpressions.select(...)

서브쿼리 만드는 도구. from()과 달리 혼자 실행되지 않고 다른 쿼리 안에 끼워 넣을 조각이에요. 그래서 fetch()가 없어요.

.where(orderItem.order.eq(order))

바깥 쿼리의 order를 안에서 참조해요(상관 서브쿼리). 바깥 행이 바뀔 때마다 "그 주문의 상품들"만 세요.

orderItem.order.count() · orderPrice.sum()

NumberPath엔 집계 메서드가 있어요. count는 Long, int 필드의 sum은 Integer라서 제네릭 타입이 달라요.

select(order, member, orderItem, orderCnt, orderSum)

5개를 꺼내니 Object[]의 [0]~[4]가 차례로 대응해요.

oi2_0, oi3_0

같은 QOrderItem.orderItem을 썼지만 Hibernate가 서브쿼리마다 별칭을 따로 붙여서 바깥의 oi1_0과 섞이지 않았어요.

필기에 같이 있던 것

@Query(..., nativeQuery = true)

자식 생성자에서 부모 생성자를 먼저 부르는 것. 부모 필드(age)는 부모가 초기화해요. Impl의 super(Order.class)도 같은 문법.
