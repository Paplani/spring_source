01 · 자바 기초

클래스와 객체, 필드와 메서드

자바는 모든 코드가 클래스 안에 있어야 하는 언어예요. 파이썬처럼 파일 아무 데나 함수를 둘 수 없어요. 그래서 자바를 읽는다는 건 "어떤 클래스가 있고, 그 클래스가 무엇을 가지고(필드) 무엇을 하는지(메서드)"를 읽는 일이에요.

클래스 class · 설계도

"책이라면 이런 값들을 가지고 이런 일을 할 수 있다"를 적어 둔 설계도예요. 붕어빵 틀이라고 생각하면 돼요. 설계도 자체는 실제 책이 아니에요.

객체 · 인스턴스 object · 실물

설계도로 실제로 만들어 낸 것이에요. 틀에서 찍어 낸 붕어빵이에요. DB에 책이 100권 있으면 Book 객체가 100개 생길 수 있어요. 객체와 인스턴스는 거의 같은 말이에요.

객체를 얻는 방법은 두 가지예요. new로 직접 찍어 내거나, 누군가 만들어서 돌려준 것을 받아요.

객체가 가지고 있는 값이에요. 책의 번호, ISBN, 제목, 가격, 저자. 클래스 안, 메서드 바깥에 적어요.

메서드 method · 하는 일(동사)

객체가 할 수 있는 일이에요. 파이썬의 함수와 같은데 반드시 어떤 클래스 안에 있어요. 그래서 메서드를 부를 땐 "누구의" 메서드인지 앞에 붙여요: book.changePrice(...), bookRepository.save(...).

}
"책아, 네 가격을 바꿔" 하는 일. 책 자신의 값을 바꾸는 일이라 Book 클래스 안에 있어요(07 탭에서 다시 봐요).

this "나 자신"

메서드 안에서 "지금 이 객체 자신"을 가리켜요. 위 this.price = price;에서 왼쪽 this.price는 이 책의 필드, 오른쪽 price는 매개변수로 받은 새 값이에요. 이름이 같아서 this로 구분해요.

03 · 자바 기초

이름표와 규칙

코드가 "하는 일"은 아니지만, 누가 쓸 수 있는지, 바뀔 수 있는지, 누가 어떻게 다룰지를 정하는 표시들이에요.

접근제어자 public · private

public은 다른 클래스에서도 쓸 수 있고, private은 이 클래스 안에서만 쓸 수 있어요. 보통 필드는 private으로 숨기고, 밖에서 쓸 메서드만 public으로 열어요(캡슐화). 밖에서 책 가격을 마음대로 고치지 못하게 하고, 고치려면 정해진 메서드(changePrice)를 거치게 하려는 거예요.

final 한 번 정하면 못 바꿈

book · service/BookService.java:24
private final BookRepository bookRepository; // 스프링이 생성자로 넣어줌
Service가 쓸 창고를 한 번 받으면 바꾸지 않겠다는 표시예요. 누가 넣어 주는지는 바로 아래 "생성자"에서 봐요.

생성자 constructor · 객체가 처음 만들어질 때 실행

객체를 new로 만들 때 딱 한 번 실행되는 특별한 메서드예요. 클래스와 이름이 같고 반환 타입이 없어요(01 탭의 basic Board 코드). 우리 코드에선 Lombok이 대신 만들어 줘서 직접 보이지 않아요.

  • @NoArgsConstructor: 빈 생성자. JPA가 DB에서 꺼낼 때 빈 객체를 먼저 만들고 값을 채워요 (Book.java:18 주석).
  • @AllArgsConstructor, @Builder: 모든 값을 한 번에 넣어 만드는 방법.
  • @RequiredArgsConstructor: final 필드를 받는 생성자. 스프링이 이 생성자로 BookRepository를 넣어 줘요. 이걸 의존성 주입(DI)이라고 불러요 (BookService.java:21, 자세히는 10 탭).

어노테이션 @ · 이름표

클래스나 메서드, 필드 위에 붙여서 "이건 이런 역할이야"라고 스프링이나 JPA, Lombok에 알려 주는 표시예요. 코드가 하는 일이 아니라 누가 이 코드를 어떻게 다룰지를 정해요. 전체 목록은 참고의 어노테이션 사전 탭에 있어요.

@Service         // 이건 업무 담당이야, 스프링이 하나 만들어 관리해
@RestController  // 이건 요청 받는 창구야, 응답은 JSON으로

패키지는 자바 파일의 주소예요. 다른 폴더의 클래스를 쓰려면 import로 정확한 주소를 알려 줘야 해요.

인터페이스, 추상 클래스, 상속

Repository가 왜 interface인지, board의 BaseEntity는 왜 abstract class인지, Querydsl Impl은 왜 extends와 implements를 같이 쓰는지가 전부 이 탭 내용이에요.

인터페이스 interface · 약속 목록

"이런 메서드가 있다"고 이름만 적고 내용(중괄호 안)은 비워 둔 목록이에요. 내용은 다른 누군가가 채워요. BookRepository는 인터페이스라서 우리가 메서드 이름만 적으면 스프링이 내용을 만들어 줘요.

중괄호 없이 세미콜론으로 끝나요. 이름 규칙(findBy + 필드명)을 보고 스프링이 SQL을 만들어요.

interface와 extends

interface는 "이런 메서드가 있다"는 약속만 적은 틀이에요. Repository가 interface인 이유는 몸통(구현)을 스프링이 실행할 때 자동으로 만들어 주기 때문이에요.

Repository 안의 default 메서드

Repository는 interface라 지금까지 몸통 없는 선언(Book findByIsbn(String isbn);)만 썼어요. 검색 조건을 만드는 코드는 Spring이 이름으로 짐작해 줄 수 없으니 직접 써야 하는데, interface 안에 몸통을 쓰려면 default가 필요해요. 주석의 "1. 구현 방법이 없는 추상 메소드 / 2. 아래 방법"이 이 두 종류예요.

필기에 같이 있던 것

@Query(..., nativeQuery = true)

기본 @Query는 JPQL(Entity 기준, from Book b). nativeQuery = true면 실제 SQL(테이블 기준)을 그대로 보내요. findByTitle2가 이 예예요. Oracle 전용 문법을 써야 할 때만 쓰고, DB가 바뀌면 고쳐야 해요.

super(age)

자식 생성자에서 부모 생성자를 먼저 부르는 것. 부모 필드(age)는 부모가 초기화해요. Impl의 super(Order.class)도 같은 문법.

@SuperBuilder

그냥 @Builder는 자기 필드만 builder에 넣어요. 부모 필드까지 .age(25).name("홍길동")처럼 쓰려면 부모와 자식 모두에 @SuperBuilder를 붙여요. PageRequestDto에 붙은 이유 → 30 탭.

List · 람다 · Optional

List와 제네릭

List는 interface, ArrayList는 실제 구현이에요. 그래서 왼쪽은 List, 오른쪽은 new ArrayList로 써요.

demo의 StudentService가 처음 배운 방식이에요. Entity 목록을 돌면서 DTO로 옮겨 담아요.

stream + 람다로 같은 일

람다 읽는 법

새 메서드가 필요할 때 차례로 물어보기

  1. 요청 주소를 받거나 응답을 내보내는 일인가? → Controller. 내용은 Service 메서드 하나 부르고 끝내는 게 보통이에요 (BookController.java:47 return service.readId(id);).
  2. DB에서 찾기·저장·삭제하는 일 자체인가? → Repository. 기본은 공짜(Book.java:46–50 메모), 특별한 조건만 이름을 적어 추가 (BookRepository.java:18).

  4. 위 셋을 조합하는 순서·판단·변환인가? → Service. 예: "찾고 → 가격 바꾸고 → 저장" (BookService.java:88–95).

폴더와 파일의 역할

스프링 프로젝트는 폴더 위치가 곧 규칙이에요. 파일을 엉뚱한 곳에 두면 코드가 맞아도 스프링이 못 찾아요.

꼭 지켜야 하는 위치 규칙 3가지

  1. 모든 코드는 시작 클래스의 패키지 아래에. BookApplication이 com.example.book에 있으니, com.example.book.xxx 안에 있어야 스프링이 찾아서 Bean으로 만들어요. 이걸 컴포넌트 스캔이라고 해요.
  2. 테스트도 시작 클래스 패키지 아래에. src/test/java/com/example/book/ 또는 그 하위 폴더(book/, shop/ …)에 두고, 첫 줄 package도 폴더와 같게(package com.example.book.shop;). 시작 클래스 패키지 바깥에 두면 "Unable to find a @SpringBootConfiguration" 에러가 나요.
  3. 파일 이름 = public 클래스 이름. Team.java 안에는 public class Team만. Team copy.java처럼 복사본이 있으면 같은 클래스가 두 개라 에러가 나요.

Bean과 의존성 주입

스프링을 쓰면 new BookService()를 직접 쓰지 않아요. 스프링이 대신 만들어서 필요한 곳에 넣어 줘요. 이게 스프링의 핵심이에요.

서버가 켜질 때 일어나는 일

  1. BookApplication의 main()이 실행돼요. @SpringBootApplication이 붙어 있어요.

  2. com.example.book 아래 모든 패키지를 훑으면서 @Controller, @Service, @Repository, @Configuration이 붙은 클래스를 찾아요 (컴포넌트 스캔).

  3. 찾은 클래스마다 객체를 딱 하나씩 만들어 보관해요. 이 객체를 Bean, 보관하는 곳을 스프링 컨테이너라고 해요.

  4. Bean끼리 필요한 걸 서로 넣어 줘요. BookController는 BookService가, BookService는 BookRepository와 ModelMapper가 필요하죠. 이걸 의존성 주입(DI)이라고 해요.

  5. 8080 포트에서 요청을 기다려요. "Started BookApplication" 로그가 뜨면 준비 완료.

생성자 주입: final + @RequiredArgsConstructor

final을 빼먹으면?

@RequiredArgsConstructor는 final 필드만 생성자에 넣어요. final이 없으면 주입이 안 돼서 그 필드는 null이고, 쓰는 순간 NullPointerException이 나요.

테스트에서는 @Autowired

테스트 클래스는 JUnit이 만들기 때문에 생성자 주입 대신 필드에 @Autowired를 붙여 받아요.

라이브러리 객체는 @Bean으로

ModelMapper는 남이 만든 클래스라 @Service를 붙일 수 없어요. 그래서 설정 클래스에서 직접 만들어 Bean으로 등록해요.

패키지가 다르면 Bean이 안 생겨요

memo에서 복사해 온 RootConfig의 패키지가 com.example.memo.config로 남아 있으면 book 스캔 범위 밖이라 ModelMapper Bean이 없어요. 그래서 BookService를 못 만들고 서버가 안 떠요.

DB는 테이블끼리 FK(외래키) 컬럼 하나로 연결하고, 자바는 필드에 객체를 넣어서 연결해요. JPA가 이 둘을 이어 주는데, 어떤 관계냐에 따라 FK 위치와 SQL 모양이 달라져요.

먼저 알아 둘 두 단어: 주인과 mappedBy

  • 연관관계의 주인 = 자기 테이블에 FK 컬럼이 있는 쪽. @JoinColumn을 붙여요. FK 값을 넣고 바꾸는 건 주인만 할 수 있어요.
  • mappedBy = "FK는 저쪽 필드가 관리해요. 나는 읽기만 해요." 반대쪽(주인이 아닌 쪽)에 붙이고, 이쪽 테이블엔 컬럼이 안 생겨요. 값은 주인 필드의 이름을 적어요 (mappedBy = "team" → TeamMember의 team 필드).
  • DB의 FK는 방향이 없어서 양쪽에서 join할 수 있지만, 자바는 필드가 있는 쪽에서만 접근할 수 있어요. 양쪽에 필드를 두면 양방향, 한쪽만 두면 단방향.

LAZY와 EAGER: 정확히 무엇이 다른가

둘 다 "연관된 객체를 가져온다"는 건 같아요. 다른 건 언제 SELECT를 보내느냐 하나예요.

EAGER (즉시 로딩)

주인 엔티티를 조회하는 그 순간 연관 객체도 같이 가져와요. findById면 left join 한 번으로, findAll이면 조회 직후 추가 select로.

→ 객체를 받았을 때 이미 팀이 진짜 데이터로 채워져 있음.

자바 객체만 바뀌었어요. 영속성 컨텍스트는 처음 상태(스냅샷)를 기억하고 있어요.

em.flush → update

flush = "모아 둔 변경을 DB에 SQL로 보내라". 스냅샷과 비교해서 name이 바뀐 걸 발견하고 update를 만들었어요. save를 부르지 않았는데도 update가 나간 것 = 변경 감지(dirty checking).

테스트 끝 → 롤백

테스트 클래스에 @Transactional이 있으면 스프링은 테스트가 끝날 때 자동으로 롤백해요. 실행 후 DB를 확인해 보니 locker 8번은 없었어요 (1, 2번만 있음). id 번호만 소모돼요.

단어뜻
flush쌓아 둔 SQL을 DB에 보내기. 아직 확정 아님 (롤백 가능)
commit트랜잭션 확정. commit 직전에 자동으로 flush가 일어나요
rollback트랜잭션 안에서 보낸 SQL을 전부 취소

1차 캐시: 같은 걸 두 번 찾으면

연관관계 탭의 LockerTest.read2()에서 sportsMemberRepository.findById(1L)이 SQL 없이 끝난 이유예요.

  1. 트랜잭션 안에서 엔티티를 조회하면 영속성 컨텍스트에 (SportsMember, 1) → 객체로 보관돼요.

  2. 같은 트랜잭션에서 같은 id를 다시 찾으면 DB에 가기 전에 여기서 먼저 찾아요. 있으면 SQL 없이 그 객체를 돌려줘요.

  3. 트랜잭션이 끝나면 비워져요. 그래서 @Transactional이 없는 read()에서는 매번 select가 나가요.

@Transactional과 변경 감지 다시 보기

여기엔 @Transactional이 없어서, findById가 끝나는 순간 memo는 준영속이에요. 그 뒤에 바꿔도 변경 감지가 안 일어나서 DB에 반영되지 않아요. 고치는 방법은 둘 중 하나:

@Transactional 붙이기

메서드 동안 영속 상태 유지 → 끝날 때 commit 전 flush → 변경 감지로 update.

save(memo) 호출

book의 BookService.update 방식. 준영속 객체를 다시 합쳐(merge) update.

@Transactional은 두 종류가 있어요

PersistenceTest와 LockerTest는 jakarta.transaction.Transactional을 import했어요. 스프링에서도 동작하지만, 보통은 org.springframework.transaction.annotation.Transactional을 써요 (readOnly = true 같은 옵션이 있어요). 자동 import에서 고를 때 스프링 쪽을 고르세요.

테스트 데이터가 안 남는다면

테스트 클래스나 메서드에 @Transactional이 있으면 끝나고 롤백돼요. insert 테스트에는 붙이지 말거나, 남기고 싶으면 @Commit(또는 @Rollback(false))을 함께 붙여요.

board에서 다시 만나요

join과 Tuple

주문과 주문자를 한 번에 꺼내는 쿼리예요. 두 종류의 엔티티를 함께 select하면 결과가 Tuple이라는 묶음으로 와요.

query.join(member)

inner join. 주문자가 없는 주문은 빠져요. 주문자 없는 것도 보려면 leftJoin.

.on(order.member.eq(member))

join 조건. "주문의 member가 이 member와 같다" = o.member_member_id = m.member_id. 엔티티끼리 비교하면 PK로 비교돼요.

select(order, member)

두 개를 꺼내니 JPQLQuery<Order>가 아니라 JPQLQuery<Tuple>이 돼요.

t.toArray()

Tuple을 Object[]로. [0]이 Order, [1]이 Member. 꺼낼 땐 형변환이 필요해요.

stream().map(...).collect(...)

React의 result.map(t => t.toArray())와 같아요. 자바는 List에 바로 map이 없어서 stream으로 바꿨다가 다시 List로 모아요.

Tuple에서 하나씩 꺼내기

Object[]로 바꾸지 않고 t.get(order), t.get(member)처럼 Q객체를 열쇠로 꺼내면 형변환 없이 타입이 맞게 나와요. 다만 Tuple은 Querydsl 타입이라 Repository 밖(Service, Controller)으로 내보내지 않는 게 보통이에요. 수업 코드가 Object[]로 바꿔서 돌려준 이유예요.

member_member_id 라는 컬럼 이름

Order의 member 필드에 @JoinColumn이 없어서 FK 이름이 "필드명_상대PK컬럼명" = member + _ + member_id로 정해졌어요. 이름을 정하고 싶으면 @JoinColumn(name = "member_id").

BaseEntity와 세 Entity의 연결

board의 Entity는 두 가지가 새로워요. 공통 부모(BaseEntity)를 상속하는 것, 그리고 필드의 타입이 다른 Entity라는 것.

BaseEntity: 날짜를 한 곳에 적고 물려주기

게시글, 회원, 댓글 모두 "언제 만들었고 언제 고쳤는지"가 필요해요. 매번 적는 대신 부모 클래스에 한 번 적고 extends로 물려받아요.

abstract class

"이걸로 직접 객체를 만들지는 않는다"는 부모 전용 설계도. new BaseEntity()는 못 해요. (04 탭 비교표)

@MappedSuperclass

BaseEntity라는 테이블은 따로 만들지 말고, 자식 테이블(board, board_member, reply)에 이 칸들을 넣어 달라는 표시.

@EntityListeners(AuditingEntityListener.class)

저장·수정 순간을 지켜보는 감시자를 붙여요. 감시자가 시각을 채워 넣어요.

@CreatedDate · @LastModifiedDate

처음 저장할 때 / 고칠 때마다 현재 시각을 자동 기록.

@Column(updatable = false)

만든 날짜는 수정할 때 UPDATE 문에서 빼요. 한 번 정해지면 안 바뀌게.

@EnableJpaAuditing

BoardApplication.java:7. 이게 있어야 위 감시자가 실제로 동작해요. 빠지면 날짜가 null로 남아요.

세 Entity 모두 날짜 필드를 직접 안 적었는데도 갖고 있어요. BoardService.java:101의 board.getCreatedDate()는 부모의 @Getter가 만든 메서드를 물려받은 거예요.

@ManyToOne

글 여러 개(Many) → 작성자 하나(One). board 테이블에 FK 컬럼이 생기는 쪽이에요. (15 탭)

게시글을 꺼낼 때 작성자는 바로 조회하지 않고, getWriter()를 실제로 쓸 때 조회해요. (16 탭)

optional = false

작성자 없는 게시글은 없다. FK 컬럼이 NOT NULL이 돼요.

@JoinColumn(name = "member_id")

FK 컬럼 이름. Member의 PK가 email이라 이 칸에는 이메일 글자가 들어가요.

@OneToMany(mappedBy = "board")

반대 방향 목록. FK는 Reply 쪽(Reply.board)에 있고, 여기는 "Reply의 board 필드를 보고 따라와"라는 뜻이라 컬럼이 생기지 않아요.

@Builder.Default

Board.builder()로 만들 때도 빈 목록(new ArrayList)을 유지해요. 없으면 replies가 null이 돼요.

@JoinColumn이 없어서 FK 컬럼 이름은 기본 규칙 "필드명_상대PK" → board_bno가 돼요.

@ToString(exclude)를 붙인 이유

@ToString(exclude = { "writer", "replies" })(Board.java:25), @ToString(exclude = {"board"})(Reply.java:19). Board를 출력할 때 replies를, 그 Reply를 출력할 때 다시 board를 출력하면 끝없이 돌아요. 또 LAZY 필드를 출력하려다 추가 조회가 일어나요. 그래서 연결된 Entity 필드는 출력에서 빼요.

클래스 위의 @Transactional은 모든 메서드를 하나의 DB 작업으로 묶어요. 이게 update에서 save를 생략할 수 있는 이유예요(아래). 창고를 두 개 들고 있는 건 삭제할 때 댓글 창고도 필요해서예요.

메서드별로

insert(BoardDto) · 39–43줄

DTO → Entity(dtoToEntity) → save → 새 bno 리턴. BookService.create와 같은 흐름이에요.

update(BoardDto) · 45–53줄
