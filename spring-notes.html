한 줄로 외우기

요청은 내려가고, 결과는 올라와요

화면 → Controller → Service → Repository → DB
DB → Entity → (Service가 변환) → DTO → Controller → JSON → 화면

왜 굳이 나눌까?

  • 고칠 곳이 명확해져요. 주소가 틀리면 Controller, 규칙이 틀리면 Service, 조회가 틀리면 Repository를 보면 돼요.

  • DB 구조를 숨길 수 있어요. Entity는 테이블 모양 그대로라 비밀번호 같은 값이 섞일 수 있어서, 화면엔 DTO만 보내요.

클래스와 객체

자바는 모든 코드가 클래스 안에 있어요. 클래스는 설계도, 객체는 설계도로 찍어 낸 실물이에요. basic 프로젝트의 Board, User가 이걸 연습한 코드예요.

id는 왜 Long일까?

기본 타입 long은 비어 있을 수 없어서 기본값이 0이에요. 객체 타입 Long은 null(값 없음)이 될 수 있어요. 새로 저장하기 전 Entity는 아직 id가 없으니 null이어야 해서 Long을 써요. 반대로 price는 항상 있으니 int.

클래스의 구성: 필드, 생성자, 메서드

접근 제어자

  • public: 어디서든 접근 가능
  • private: 이 클래스 안에서만. 필드는 보통 private으로 숨기고 메서드로만 다루게 해요 (캡슐화).

setter 대신 의미 있는 메서드

Entity에서는 @Setter를 빼고 필요한 변경만 메서드로 열어 두는 걸 연습했어요. 아무 값이나 바꿀 수 있는 setter보다 "가격만 바꿀 수 있다"는 의도가 드러나요.

생성자

처음 만들 때 한 번에 채우기. new Board(1L, "제목")

setter / change 메서드

만든 다음에 값을 바꾸기. book.changePrice(42000)

enum: 정해진 값만 허용

interface와 extends

interface는 "이런 메서드가 있다"는 약속만 적은 틀이에요. Repository가 interface인 이유는 몸통(구현)을 스프링이 실행할 때 자동으로 만들어 주기 때문이에요.

순환 상속

TeamRepository extends TeamRepository처럼 자기 자신을 상속하면 "Cycle detected" 에러예요. 상속 대상은 항상 JpaRepository<엔티티, Long>.

List · 람다 · Optional

Service 코드에서 매일 보는 세 가지예요. 여러 개 담기(List), 하나씩 바꾸기(stream + 람다), 없을 수도 있는 값(Optional).

List와 제네릭

List는 interface, ArrayList는 실제 구현이에요. 그래서 왼쪽은 List, 오른쪽은 new ArrayList로 써요.

for문으로 하나씩 바꾸기

demo의 StudentService가 처음 배운 방식이에요. Entity 목록을 돌면서 DTO로 옮겨 담아요.

stream + 람다로 같은 일

람다 읽는 법

book -> mapper.map(book, ...)는 "book을 받아서 오른쪽 결과를 돌려주는 짧은 함수"예요. JS의 화살표 함수 book => ...와 같은데, 자바는 ->(하이픈)을 써요. =>를 쓰면 문법 에러예요.

반복해서 여러 개 만들기

05 · 스프링

Bean과 의존성 주입

스프링을 쓰면 new BookService()를 직접 쓰지 않아요. 스프링이 대신 만들어서 필요한 곳에 넣어 줘요. 이게 스프링의 핵심이에요.

서버가 켜질 때 일어나는 일

  1. BookApplication의 main()이 실행돼요. @SpringBootApplication이 붙어 있어요.

  2. com.example.book 아래 모든 패키지를 훑으면서 @Controller, @Service, @Repository, @Configuration이 붙은 클래스를 찾아요 (컴포넌트 스캔).

  3. 찾은 클래스마다 객체를 딱 하나씩 만들어 보관해요. 이 객체를 Bean, 보관하는 곳을 스프링 컨테이너라고 해요.

  4. Bean끼리 필요한 걸 서로 넣어 줘요. BookController는 BookService가, BookService는 BookRepository와 ModelMapper가 필요하죠. 이걸 의존성 주입(DI)이라고 해요.

  5. 8080 포트에서 요청을 기다려요. "Started BookApplication" 로그가 뜨면 준비 완료.

생성자 주입: final + @RequiredArgsConstructor

final을 빼먹으면?

@RequiredArgsConstructor는 final 필드만 생성자에 넣어요. final이 없으면 주입이 안 돼서 그 필드는 null이고, 쓰는 순간 NullPointerException이 나요.

테스트에서는 @Autowired

테스트 클래스는 JUnit이 만들기 때문에 생성자 주입 대신 필드에 @Autowired를 붙여 받아요.

라이브러리 객체는 @Bean으로

ModelMapper는 남이 만든 클래스라 @Service를 붙일 수 없어요. 그래서 설정 클래스에서 직접 만들어 Bean으로 등록해요.

패키지가 다르면 Bean이 안 생겨요

memo에서 복사해 온 RootConfig의 패키지가 com.example.memo.config로 남아 있으면 book 스캔 범위 밖이라 ModelMapper Bean이 없어요. 그래서 BookService를 못 만들고 서버가 안 떠요.

JPA와 데이터베이스

JPA는 자바 객체(Entity)와 DB 테이블을 연결해 주는 기술이에요. SQL을 직접 쓰지 않고 자바 메서드로 넣고 꺼내요. 실제 SQL은 Hibernate가 만들어서 콘솔에 보여 줘요.

Entity: 테이블 설계도

자주 쓰는 설정뜻예
@Table(name="...")테이블 이름 직접 지정Student → studenttbl, Memo → memotbl
@Column(name="...")컬럼 이름 지정Memo.id → mno
length문자 길이length = 50
@Enumerated(EnumType.STRING)enum을 글자로 저장FRESHMAN (기본은 0,1,2 숫자)

Repository가 공짜로 주는 메서드

메서드하는 일SQL
save(entity)id가 없으면 추가, 있으면 수정INSERT / UPDATE

메서드 이름으로 쿼리 만들기

규칙에 맞게 이름만 지으면 JPA가 SQL을 만들어 줘요. 필드 이름과 정확히 같아야 해요.

save는 추가일까 수정일까?

  1. 추가: Book.builder().isbn(...).build()로 만든 객체는 id가 null이에요. save하면 INSERT하고, 새 id가 채워진 객체를 돌려줘요.

  2. 수정: findById로 꺼낸 객체는 id가 있어요. 값을 바꾸고 save하면 UPDATE해요.

memo의 update는 저장이 안 될 수 있어요

MemoService.update()는 changeText만 하고 save도 @Transactional도 없어요. 그래서 DB에 반영되지 않아요. 둘 중 하나를 넣어야 해요. @Transactional을 붙이면 메서드가 끝날 때 바뀐 값을 JPA가 알아서 UPDATE해요 (변경 감지). 영속성 컨텍스트 탭에서 실제 로그로 확인할 수 있어요.

날짜 자동 기록 (Auditing)

demo, memo에서 쓴 기능이에요. 세 군데를 모두 챙겨야 동작해요.

DTO와 ModelMapper

DTO(Data Transfer Object)는 화면과 주고받는 데이터 상자예요. Entity는 DB 안쪽 모양이고, DTO는 바깥에 보여 줄 모양이에요.

Entity

DB 테이블과 1:1. 연관된 객체, 비밀번호 같은 내부 값도 들어 있어요. Repository가 다뤄요.

DTO

요청·응답에 필요한 값만. 화면이 원하는 대로 자유롭게 모양을 바꿀 수 있어요. Controller가 다뤄요.

Service가 둘 사이를 변환해요. 들어올 땐 DTO → Entity, 나갈 땐 Entity → DTO.

요청용 DTO와 응답용 DTO

memo에서는 둘을 나눴어요. 메모를 새로 쓸 땐 text만 있으면 되니까 요청용엔 text만 있어요.

손으로 옮기기 vs ModelMapper

규칙은 하나: 필드 이름을 같게

Book의 title과 DTO의 title처럼 이름이 같아야 복사돼요. LOOSE 설정이라 userName과 user_name 정도 차이는 맞춰 줘요.

map에 null을 넣으면

mapper.map(null, ...)은 "source cannot be null" 예외예요. 조회 결과가 없을 수 있으면 먼저 Optional로 확인하세요.

2-1. Book.java: 테이블 설계도

src/main/java/com/example/book/entity/ 폴더를 만들고 그 안에 만들어요.

import jakarta.persistence.*

JPA 어노테이션들. jakarta로 시작하는 걸 골라야 해요.

import lombok.*

코드를 대신 만들어 주는 Lombok 어노테이션들.

@Entity

"이 클래스는 DB 테이블이다." 클래스 이름 Book → 테이블 이름 book.

@Getter @Setter

모든 필드의 getTitle(), setTitle() 등을 만들어 줘요. ModelMapper와 JSON 변환이 getter를 써요.

@NoArgsConstructor

빈 생성자 new Book(). JPA가 DB에서 읽은 값을 담을 때 이걸로 먼저 만들어요. 없으면 에러.

@AllArgsConstructor

모든 필드를 받는 생성자. 바로 아래 @Builder가 내부에서 써요.

@Builder

Book.builder().title("…").price(36000).build()처럼 원하는 필드만 이름 붙여 채워서 만들 수 있게 해요.

@ToString

System.out.println(book) 하면 Book(id=14, isbn=…)처럼 보이게.

@Id

이 필드가 기본키(PK). 한 줄을 구분하는 번호.

@GeneratedValue(IDENTITY)

번호는 DB가 1, 2, 3… 자동으로 매겨요. 그래서 저장 전엔 id가 null.

private Long id;

null이 될 수 있어야 해서 long이 아닌 Long.

@Column(nullable = false, unique = true)

isbn은 비어 있으면 안 되고(NOT NULL), 같은 값이 두 번 들어갈 수 없어요(UNIQUE).

private int price;

가격은 항상 있으니 기본 타입 int.

changePrice(int price)

가격을 바꾸는 전용 메서드. 수정(Update) 때 Service가 이걸 불러요.

서버를 켜면 만들어지는 테이블

ddl-auto=update 덕분에 콘솔에 대략 이런 SQL이 찍히고 테이블이 생겨요.

Book Entity와 이름이 똑같아요. ModelMapper는 이름이 같은 필드끼리 값을 복사하니까 이게 중요해요.

@Data

@Getter, @Setter, @ToString 등을 한 번에. 그래서 위의 @Getter, @Setter, @ToString은 사실 중복이에요 (에러는 아니에요).

Controller에서 dto.setId(id)를 쓰고, JSON 변환도 setter를 써요.

지금은 모양이 같지만 역할이 달라요. Entity는 DB 모양이라 바뀌면 테이블이 바뀌어요. DTO는 화면이 원하는 모양이라 자유롭게 바꿔도 돼요. 예를 들어 나중에 Book에 "내부 메모" 컬럼이 생겨도 DTO에 안 넣으면 화면엔 안 나가요. memo 프로젝트처럼 요청용(MemoRequestDto: text만)과 응답용(MemoDto: id, 날짜까지)을 나누기도 해요.

로그 볼 때 체크 4가지

  1. SQL이 몇 개인가? findById 한 번에 select가 2개 이상이면 연관 객체를 따로 가져온 거예요. 목록 조회에서 같은 모양 select가 반복되면 N+1이에요 (LAZY와 EAGER 탭).

  2. join이 있나? 어떤 join인가? left join이면 연관 객체를 함께, 없으면 따로 또는 나중에.

  3. where 조건과 binding 값이 맞나? 엉뚱한 컬럼(isbn=?에 제목이 들어감)이나 없는 id가 여기서 보여요.

  4. println 결과가 SQL 사이 어디에 찍혔나? 출력보다 SQL이 먼저면 미리 가져온 것(EAGER), 출력 직전에 SQL이 끼어들면 그때 가져온 것(LAZY)이에요. 테스트에 System.out.println("--- 여기")를 넣으면 경계가 잘 보여요.

LAZY와 EAGER: 정확히 무엇이 다른가

둘 다 "연관된 객체를 가져온다"는 건 같아요. 다른 건 언제 SELECT를 보내느냐 하나예요.

EAGER (즉시 로딩)

주인 엔티티를 조회하는 그 순간 연관 객체도 같이 가져와요. findById면 left join 한 번으로, findAll이면 조회 직후 추가 select로.

→ 객체를 받았을 때 이미 팀이 진짜 데이터로 채워져 있음.

LAZY (지연 로딩)

연관 객체 자리에 프록시(id만 아는 가짜 객체)를 넣어 두고, getName()처럼 실제 값이 필요한 순간에 select를 보내요.

→ 그 순간 DB 연결(세션)이 열려 있어야 함.

영속성 컨텍스트

JPA가 엔티티를 DB에 바로 쓰지 않고 잠시 들고 있는 메모리 공간이에요. "1차 캐시"와 "변경 감지"가 여기서 일어나요. LAZY 로딩이 가능한 것도, 위에서 SQL 없이 객체가 나온 것도 이것 때문이에요.

엔티티의 4가지 상태

비영속 (new)그냥 new로 만든 자바 객체. JPA는 모름Locker.builder()…build()

준영속 (detached)관리하다가 손을 놓은 상태. 바꿔도 DB 반영 안 됨, LAZY 불가트랜잭션이 끝난 뒤의 객체

3. changeName → SQL 없음

자바 객체만 바뀌었어요. 영속성 컨텍스트는 처음 상태(스냅샷)를 기억하고 있어요.

flush = "모아 둔 변경을 DB에 SQL로 보내라". 스냅샷과 비교해서 name이 바뀐 걸 발견하고 update를 만들었어요. save를 부르지 않았는데도 update가 나간 것 = 변경 감지(dirty checking).

테스트 끝 → 롤백

테스트 클래스에 @Transactional이 있으면 스프링은 테스트가 끝날 때 자동으로 롤백해요. 실행 후 DB를 확인해 보니 locker 8번은 없었어요 (1, 2번만 있음). id 번호만 소모돼요.

  1. 트랜잭션 안에서 엔티티를 조회하면 영속성 컨텍스트에 (SportsMember, 1) → 객체로 보관돼요.

  2. 같은 트랜잭션에서 같은 id를 다시 찾으면 DB에 가기 전에 여기서 먼저 찾아요. 있으면 SQL 없이 그 객체를 돌려줘요.

  3. 트랜잭션이 끝나면 비워져요. 그래서 @Transactional이 없는 read()에서는 매번 select가 나가요.

@Transactional과 변경 감지 다시 보기

여기엔 @Transactional이 없어서, findById가 끝나는 순간 memo는 준영속이에요. 그 뒤에 바꿔도 변경 감지가 안 일어나서 DB에 반영되지 않아요. 고치는 방법은 둘 중 하나:

@Transactional 붙이기

메서드 동안 영속 상태 유지 → 끝날 때 commit 전 flush → 변경 감지로 update.

save(memo) 호출

book의 BookService.update 방식. 준영속 객체를 다시 합쳐(merge) update.

@Transactional은 두 종류가 있어요

PersistenceTest와 LockerTest는 jakarta.transaction.Transactional을 import했어요. 스프링에서도 동작하지만, 보통은 org.springframework.transaction.annotation.Transactional을 써요 (readOnly = true 같은 옵션이 있어요). 자동 import에서 고를 때 스프링 쪽을 고르세요.

테스트 데이터가 안 남는다면

테스트 클래스나 메서드에 @Transactional이 있으면 끝나고 롤백돼요. insert 테스트에는 붙이지 말거나, 남기고 싶으면 @Commit(또는 @Rollback(false))을 함께 붙여요.
